## 0. 先说清楚「两套东西」

桌面上曾经同时出现过两只宠物，根因就是这里：

| | DSH 插件版 | 独立桌面版（本文主角） |
|---|---|---|
| 是什么 | DSH 主程序里的一个插件 | 自己带 Electron 的一个应用 |
| 入口 | `~/.dsh/profiles/desktop/node_modules/dsh-pet/lib/index.js` | `cat-pet/plugin/lib/app.js` |
| 配置目录 | `C:\Users\lianzhi\.dsh\dsh-pet\` | `C:\Users\lianzhi\.dsh-cat\dsh-pet\` |
| 进程 | DSH 主进程 + 它拉起的 helper | 自己的 Electron 主进程 + 自己的 helper |
| 谁在画 | DSH 窗口内渲染 | 独立透明置顶窗口 |
| 形象 | 官方默认（蓝毛小女仆） | 你的大肥橘猫（`main-animation\webm\`） |

两套**共用同一份插件代码**（独立版就是用同一份源码构建出另一个入口），但
**运行时完全隔离**：不同进程、不同 HTTP 端口、不同配置目录、不同记忆库、不同语音服务。

隔离手段就一条：环境变量 `DSH_HOME`。独立版启动时把它指到 `.dsh-cat`，所有 `dshHomeDir()`
的调用（配置、记忆、日志、语音缓存、Electron 路径）都会落到那边去。

### 1.1 进程与产物

| 产物 | 大小 | 作用 |
|---|---|---|
| `lib/app.js` | ≈476 KB | 独立桌面应用主进程（Electron 入口） |
| `lib/index.js` | ≈327 KB | DSH 插件入口（cordis 插件） |

### 1.2 HTTP 路由（前缀 `/dsh-pet-<段>`）

| 路由 | 方法 | 说明 |
|---|---|---|
| `/state` | GET | **长轮询**：带 `since`+`timeout` 时挂起，状态版本变了才返回；不带走全量 |
| `/chat` | POST | 一次对话：召回 → 调模型 → 落记忆 → 写 say 叶子 |
| `/voice/speak` | POST | 合成一句，返回 `audio/mpeg` |
| `/voice/hear` | POST | 语音识别路由（**已停用**：没有 provider，回 `unsupported`） |
| `/voice/voices` | GET | 音色列表 |
| `/whisper` | POST | 手动触发一次碎碎念 |
| `/config` | GET | 合并后的成品配置 |
| `/assets/*` | GET | 动画素材（用户 `main-animation` 优先） |
| `/desktop/quit` `/desktop/reload` | POST/GET | 生命周期 |

### 1.3 鉴权

`src/standalone/request-security.ts`：

- **GET/HEAD** 基本放行（`/state`、`/config`、`/assets`、`/health`…）
- **POST 一律要令牌**：请求头 `X-DSH-Pet-Token` 或 cookie `dsh_pet_token`
- 令牌每次启动随机生成，只存在于主进程内存（`process.env.DSH_PET_APP_TOKEN`）
- 独立模式的渲染端由 `installDesktopAuth()` 注入 cookie 和自定义协议，
  所以页面里 `fetch(..., { credentials: 'include' })` 能过

   │      │      ▼
   │      │   createVoiceService().speak()
   │      │      ├─ activeVoiceProvider()  →  qwen3-tts（注册在 voice/registry.ts）
   │      │      ├─ provider.synthesize({text, rate})  →  Uint8Array(mp3)

| 环节 | 耗时 |
|---|---|
| LLM 出完整回复 | 0.85 – 1.5 s |

## 3. 记忆库：从「5 轮 JSON」到「三层 SQLite」

### 3.1 原设计（上游）

```
memory.json
{ "<素材根>": { "<petId>": { "messages": [ {role, content, ts, image?, meme?, action?} ] } } }
```

- 每轮追加 user + assistant 两条
- 下一轮只 `slice` 尾部 N 轮塞进 `history`
- **没有检索、没有语义记忆、没有情绪**，超出窗口就等于忘了

### 3.2 现在的三层

| 层 | 表 | 内容 | 怎么用 |
|---|---|---|---|
| 原文层 | `messages` | 每轮原话（含 ts、image_name） | 关键词 `LIKE` 召回，按情感衰减排序 |
| 事实层 | `memories` | 从原话里抽的短事实（过敏、喜好、住址…） | 命中即**置顶**，并强制「以这里为准」 |
| 情绪权重 | `messages.valence/arousal/dominance` | 由情绪词典打分 | 改变原文层的半衰期 |

```sql
CREATE TABLE messages (
  id INTEGER PRIMARY KEY, pet_id TEXT NOT NULL, role TEXT NOT NULL,
  content TEXT NOT NULL, ts INTEGER NOT NULL, image_name TEXT,
  valence REAL, arousal REAL, dominance REAL
);
CREATE UNIQUE INDEX ux_messages ON messages(pet_id, ts, role);

CREATE TABLE memories (
  id INTEGER PRIMARY KEY, pet_id TEXT NOT NULL, kind TEXT NOT NULL,
  content TEXT NOT NULL, importance REAL NOT NULL, confidence REAL,
  valence REAL, arousal REAL, dominance REAL, emotion TEXT,
  source_ts INTEGER, created_at INTEGER, last_used_at INTEGER,
  access_count INTEGER DEFAULT 0, archived INTEGER DEFAULT 0
);
```

### 3.3 召回打分

```
候选：SELECT … WHERE pet_id=? AND (content LIKE '%词%' OR …) AND ts < 当前窗口最早时间
      ORDER BY ts DESC LIMIT 400

每条的原始分  hit = Σ 命中关键词长度
时间衰减      decay = 0.5 ^ (天数 / 半衰期)
半衰期        原文：30 × (1 + 0.9 × |valence| × arousal)   天
              （情绪越强留得越久：中性 30 天，强烈情绪可到 80+ 天）
             事实：不衰减
角色加成      user 说的 +0.3
最终分        score = hit × (0.4 + decay) + roleBonus
             事实层再乘 1.6 并 +0.5（保证排在原文前面）
```

### 3.4 进提示词的样子

```
【关于她，你确定知道的事】
- 她对花生过敏
- 她叫练志
（这一节一律以这里为准：直接照着回答，不要反问，不要改口）

【你想起的旧事】（更早的对话，按时间排序，只在贴题时提一句）
- 2026-11-05 她：我下周三要去杭州出差……
```

### 3.5 三路召回：关键词 → 语义 → 合流

前两路是「字面」，第三路是「意思」。同一句话换种说法，前两路全瞎，第三路能捞回来。

```
① 关键词路   LIKE 直扫（见 3.3）
② 事实路     memories 表按 importance 取前 40，命中即置顶
③ 语义路     bge-m3 把查询编成 1024 维向量，和库里 vec 列做余弦
             SELECT … WHERE vec IS NOT NULL … LIMIT 1500（原文）/ 500（事实）
             score = 3.2 × sim × (0.4 + decay) + bonus
             低于阈值 0.52 的丢弃（DSH_PET_VEC_MIN 可调）
```

- 向量存 `BLOB`（Float32 小端，`encodeVec` 手写 DataView，不依赖平台字节序）
- 补历史是**后台单飞**的：`backfillVectors()` 每批 32 条，`appendTurn` 之后 `void` 调用，不阻塞回复
- 同一段内容被两路命中时只占一个名额，取高分

**为什么用 bge-m3**：中文短句效果好、1024 维、Ollama 一行拉下来就能用、和聊天模型共用显存池不额外占卡。

**实测**（`scripts/probe-vector.ts`，10 项全过）：

| 查询 | 原文（10 天前说的） | 余弦 | 结果 |
|---|---|---|---|
| 那个环保的活儿弄得怎么样了 | 我最近在赶一个海洋塑料污染的汇报材料 | 0.569 | 捞到了，纯关键词路捞不到 |
| 你记得我去看的那个展吗 | 周末去看了个展，是关于老式打字机的 | — | 捞到了 |
| 吃面的地方是不是换了个人经营 | 楼下那家面馆换老板了 | — | 捞到了，纯关键词路捞不到 |

### 3.6 为什么没用 FTS5

实测两条路都不通（`node:sqlite`，中文）：

| 分词器 | 现象 |
|---|---|
| `unicode61` | 整句中文被当成**一个 token**，搜「乳腺癌」0 命中 |
| `trigram` | 只支持 ≥3 字的串，「房东」「复查」「妈妈」全 0 命中 |

几千条消息的 `LIKE` 直扫是毫秒级，先这样跑。

### 3.7 踩过的三个坑

1. **问句被当成事实**：「我对什么过敏？」会抽出「我对什么过敏」这条"事实"，和自己的提问撞车，
   模型回「被问懵啦」。→ 加 `looksInterrogative()`，尾巴带疑问词的整条丢弃。
2. **事实留了第一人称**：「我对花生过敏」原样写进猫的系统提示，猫以为过敏的是它自己。
   → 统一转成「她对花生过敏」。
3. **召回结果被按时间重排**：最贴题的事实被挤到中间，模型抓不到重点。
   → 事实按分数在前，原文按时间在后。

| 角色 | 现在用什么 | 跑在哪 | 资源 |

| 表情包匹配 | 表情名关键词匹配 | 本机 | 0 |

> **语音输入（ASR）已于 2026-11-09 整体移除。** 现状：不启动 faster-whisper 子进程、
> 不注册 speech provider、对话弹窗没有话筒按钮、M 键不再绑定、`faster-whisper` 模型目录与

> 调用会回 `unsupported`。下面第 4.3 节留作记录，代码已不在。


### 4.1 对话模型的两个「咬人」配置

- `timeoutMs` **上限 60000**，写 90000 会让整个应用起不来，报
  `Cannot securely load standalone AI settings.`（这个异常同时覆盖「读盘失败」，别被误导）
- 思考型模型（qwen3.5）必须 `"reasoningEffort": "none"`。默认它把 token 全烧在 reasoning 上，
  `content` 回来是空的，表现为「碎碎念生成失败 reason=generate-error」。
  `think:false` 在 `/v1` 接口上无效，只有 `reasoning_effort` 生效。

### 4.2 TTS 的硬指标

| 指标 | 实测 |
|---|---|
| 模型体积 | 2.34 GB（12 个文件） |
| 加载 | 2.4 s（模型）+ 15.1 s（参考音色 prompt，启动时一次性） |
| 显存 | 2.02 GiB，峰值 2.59 GiB |
| 输出 | 24 kHz 单声道 |
| **RTF** | **1.7 – 1.95**（1 秒音频要算 1.7–1.95 秒） |
| 编码 | `lameenc` 128 kbps，4.9 s 音频 26 ms |

**RTF 1.8 是这个方案最大的体验瓶颈**：回复越长，声音越追不上，中间必然出现空白。

### 4.3 语音输入（ASR）——已移除，此节仅存档

> 2026-11-09 按用户要求整体删除：`cat-pet/asr_server.py`、`src/host/voice/whisper.ts`、
> `scripts/probe-whisper.ts`、弹窗话筒按钮、`chat/hear-control.ts`、M 键绑定全部去掉；
> `faster-whisper-large-v3-turbo` 模型目录（1.51 GB）与 `faster-whisper`/`ctranslate2` 包已卸载。

当时的设计：模型在独立 Python 进程常驻，Electron 只管 spawn 和转发。

```
麦克风 → getUserMedia → encodeWave(16k 单声道 PCM16) → base64
       → POST /voice/hear  → whisper provider → POST 127.0.0.1:8766/transcribe
       → {text} → 当成一条普通消息进对话链路
```

| 项 | 数值 |
|---|---|
| 模型 | faster-whisper **large-v3-turbo**（CTranslate2，`deepdml/faster-whisper-large-v3-turbo-ct2`，1.51 GB） |
| 加载 | 2.4 s |
| **冷启动第一次推理** | **约 20 s**（cuBLAS 初始化），所以启动后用 0.6 s 静音预热一次 |
| 热态 | 1.55 s 音频 **101 ms**（RTF 0.07）、2.34 s 音频 123 ms（RTF 0.05） |
| 显存 | 约 1.6 GB |
| 关掉 | `DSH_PET_ASR=off` |

**cuBLAS 那个坑**：ctranslate2 只认系统 PATH 里的 `cublas64_12.dll`，而我们的 CUDA 装在 torch wheel 里。
不挂目录就报 `Library cublas64_12.dll is not found or cannot be loaded`。修法是在 `import ctranslate2`
**之前**执行 `os.add_dll_directory(<torch>/lib)` 并把该目录塞进 `PATH`。

识别参数：`beam_size=5, best_of=5, temperature=0.0, condition_on_previous_text=False, vad_filter=False`
（客户端已经裁过静音，服务端再切会切掉字头）；<0.25 s 的音频直接返回空串。

## 7. 已知短板（按影响排序）

1. **TTS RTF 1.8**：声音追不上字幕式的合成速度，长回复必然出现 2–9 s 的停顿。
   要么让回复更短，要么换更快的引擎（流式 TTS），要么降采样率/精简模型。
2. **首声 6–9 s**：用户发完消息到听见第一个字，中间是空的（气泡也在等）。
   可按句切得更碎（第一片 8–10 字）把首声压到 4 s 左右。
3. **单句上限 120 字**：超出部分不念（`VOICE_SPEECH_TOTAL_MAX`）。
4. **TTS 挂了就静音**：没有自动回退到 Edge。
5. **显存偏紧**：14B（9 GB）+ TTS（2.5 GB）+ 显示 ≈ 12 GB / 16 GB，
   再叠加别的 GPU 程序就可能被换出。

| 想干什么 | 怎么做 |

## 9. 一句话总结

**它是「一个 Electron 壳 + 一个本机 HTTP 服务 + 一份伪装的 DSH 宿主 + 两个模型的缝合怪」**：
外壳和渲染是上游 dsh-pet 的，中间那层 HTTP/记忆/语音是我加的，
模型侧是一个 14B 的 Ollama 聊天模型 + 一个 0.6B 的本地克隆 TTS + 一个 bge-m3 的向量模型（语音识别已移除）。

真正的技术风险只有一个：**本地 0.6B TTS 的推理速度比实时慢 1.8 倍**。
其它的（记忆、路由、隔离、构建）都已经跑通并有测试兜底。
