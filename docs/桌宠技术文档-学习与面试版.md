## 1. 一分钟版（面试开场用这段）

> "我做了一个 Windows 桌面宠物应用：桌面上常驻一只透明置顶的 2D 猫，点开对话窗能聊天，

>
> 有意思的地方不在模型，在记忆：**模型本身没有长期记忆，所谓"记得你"其实是我在每轮对话前
> 把相关的旧事检索出来拼进 prompt**。所以我要解决三件事——写进去、记得住、捞得出来，
> 而捞得准不准直接决定它像不像真的记得。"

## 2. 全景：这是两套东西

很多人第一反应会以为"桌面宠物"是 DSH 里的插件。实际是两套，**靠环境变量隔离**：

| | A. DSH 里的插件版 | B. 独立桌面版（我做的） |
|---|---|---|
| 形态 | DSH 窗口里的浮层 | 独立 Electron 应用，自己的 exe |
| 配置目录 | `~/.dsh/dsh-pet/` | `~/.dsh-cat/dsh-pet/`（`DSH_HOME` 覆盖） |
| 包 | npm 上 `dsh-pet@0.4.3` | 本地 fork `cat-pet/plugin` |
| 用谁的模型 | DSH 的会话模型 | 自己的 `standalone-ai.json` |
| 记忆 | 自己的 `memory.json` | 同样的文件 + `memory.db` |

隔离手段只有一行：启动器里 `set DSH_HOME=C:\Users\lianzhi\.dsh-cat`。
插件的所有路径都从 `dshHomeDir()` 派生，改这一个变量就把两套东西彻底分开了。

> **面试点**：这其实是"配置与代码分离"的一个具体表现——同一份代码，靠外部注入的根目录
> 跑出两个互不干扰的实例。比 fork 一份代码去改要干净得多。

### 2.1 运行时拓扑

```
┌─────────────────────── Electron 主进程 (app.js) ────────────────────────┐
│                                                                        │
│  boot()                                                                │
│   ├─ createStandaloneAi()      读 standalone-ai.json，建 openai 客户端   │
│   ├─ createStandaloneContext() 造一个"假 DSH 宿主"（ctx 的极小子集）      │
│   ├─ startRouter()             Node http server，监听 127.0.0.1:随机端口  │
│   ├─ apply(ctx)                把 dsh-pet 插件代码挂上去                 │
│   └─ require(helper/main.js)   拉起窗口栈（透明窗、托盘、动画、气泡）      │
│                                                                        │
│  HTTP 路由（全部带 X-DSH-Pet-Token 或 cookie）                           │
│   /state  /chat  /voice/speak  /voice/voices  /config  /assets/*        │
└────────────┬──────────────────────────────────────┬────────────────────┘
             │ child_process.spawn                  │ BrowserWindow（透明/置顶/无边框）
             ▼                                      ▼
   ┌──────────────────┐                  ┌────────────────────────┐
   │ tts_server.py    │                  │ 渲染进程（宠物+气泡+对话窗）│
   │ Qwen3-TTS 常驻    │◄── HTTP :8765 ───│ 读 /state 长轮询         │
   │ 占显存约 2.5 GB   │                  │ <audio> 播 mp3           │
   └──────────────────┘                  └────────────────────────┘
             │
             ▼  另外两个"外部"依赖
   ┌──────────────────┐   ┌──────────────────┐
   │ Ollama :11434    │   │ SQLite 文件        │
   │ qwen3:14b 聊天    │   │ memory.db (WAL)   │
   │ bge-m3 向量       │   │ memory.json 原文   │
   └──────────────────┘   └──────────────────┘
```

三句话记住它：

1. **一个 Electron 进程里塞了三样东西**：主进程、HTTP 服务、以及"假装自己是 DSH 宿主"的适配层。
2. **重活全在子进程或外部服务**：TTS 是 Python 进程，LLM 和 embedding 是 Ollama，记忆是 SQLite 文件。
3. **渲染进程不碰任何模型**，它只会两件事：长轮询拿状态、POST 一句话。

## 3. 一条消息的完整旅程（含实测耗时）

用户打字 → 界面上出现气泡 + 听见声音，中间发生了什么：

| # | 步骤 | 代码位置 | 实测耗时 |
|---|---|---|---|
| 1 | 渲染端 `POST /chat`（带 cookie） | `shared/chat/send.ts` → `src/host/routes/chat.ts` | — |
| 2 | 校验令牌、取出 petId、加锁（同一只宠物串行） | `standalone/request-security.ts`、`chat-memory.ts:85` | <1 ms |
| 3 | 读 `memory.json` 拿最近 N 轮 | `chat-memory.ts:60` | 2–5 ms |
| 4 | **抽关键词 + 查向量 + 合并打分** | `memory/store.ts:539` | 15–40 ms（含一次 embedding 请求） |
| 5 | 拼 system prompt（人设 + 名字 + 时间 + 历史说明 + 召回段） | `host/persona.ts:59` + `memory/store.ts` 的 `formatRecall` | <1 ms |
| 6 | 调 `POST /v1/chat/completions` | `standalone/ai-transport.ts:100` | 0.6–1.5 s（14B，首 token 后流式拿完） |
| 7 | 复读检测：和历史上自己说过的话比相似度 | `host/chat.ts:251` | <5 ms |
| 8 | 命中就带"换个说法"重生成一次 | 同上 | +0.6–1.5 s |
| 9 | 写回 `memory.json` + 异步落 `memory.db` | `chat-memory.ts:319`、`store.ts:appendTurn` | 5–15 ms（不阻塞回复） |
| 10 | 写 `say` 叶子 → 渲染端长轮询取到 → 出气泡 | `state.writePet(petId,'say',…)` | 立即 |
| 11 | 并行：按句切片 → 逐片请求 TTS → 边合成边播 | `shared/voice.ts`、`tts_server.py` | 首片 6–9 s，后续每片 2–9 s 停顿 |

**关键观察**：第 6 步只占整个体验的 1/5。用户觉得"慢"，慢在 11。

> **面试点**：这是典型的"端到端延迟 ≠ 模型延迟"。很多人只优化 LLM，实际瓶颈在链路上其它环节。

## 4. 大模型接入层

### 4.1 用的什么协议

不是专有 SDK，是 **OpenAI 兼容的 `/v1/chat/completions`**（Ollama 实现了它）。
代码里用官方的 `openai` npm 包，只把 `baseURL` 指到 `http://127.0.0.1:11434/v1`。

为什么选这个协议而不是各家 SDK：

| 方案 | 换模型的成本 |
|---|---|
| 各厂商原生 SDK | 换一家 = 改一遍代码 |
| **OpenAI 兼容协议** | 换一家 = 改一个 `baseURL` + 一个 `model` 字符串 |
| 自建抽象层 | 要自己维护参数映射表，容易漏 |

顺带的好处：Ollama、vLLM、LM Studio、DeepSeek、通义，全都说这个协议。
这份代码的 `standalone-ai.json` 里 `protocol` 字段还能切 `anthropic`，走另一套路径。

### 4.2 参数逐个说清（面试高频）

```jsonc
{
  "model": "qwen3:14b",
  "maxTokens": 1024,      // 输出上限
  "timeoutMs": 60000,     // 整次请求的超时
  "reasoningEffort": "none",
  "temperature": 1        // 代码里写死
}
```

| 参数 | 是什么 | 这里的取值与理由 |
|---|---|---|
| `max_tokens` | **输出**的 token 上限，不含输入 | 1024。宠物回复短句，给多了只会让它啰嗦，还拖慢生成 |
| `temperature` | 采样温度。softmax 前把 logits 除以 T：T<1 更确定，T>1 更随机 | 1.0。聊天要活人感；试过降到 0.7，回复变得像客服 |
| `top_p` | 核采样。只从累计概率前 p 的词里抽 | 默认 1.0，不额外截断（temperature 已经在做这件事） |
| `top_k` | 只从概率最高的 k 个词里抽 | 默认不开；TTS 那边用了 50 |
| `repetition_penalty` | 已出现过的 token 降权 | 聊天默认 1.0；TTS 用 1.05，否则会卡在同一个字上 |
| `finish_reason` | 结束原因：`stop` 正常 / `length` 撞上限 / `tool_calls` | **必须检查**，见 4.6 |
| `reasoning_effort` | OpenAI 的新参数，Ollama 也认。`none` = 不要思考过程 | **这个项目最大的一个坑**，见 4.6 |

> 注意：`max_tokens` 是输出；整个 prompt 的长度受模型 **context window** 限制（qwen3 默认 32K，
> Ollama 里可以调 `num_ctx`）。输入 + 输出超了会被截断，表现为"它没看到前面的话"。

### 4.3 量化、显存、KV cache（算账能力）

面试官很爱问"为什么 14B 能跑在 16G 显卡上"。

**量化**：模型权重本来是 16 位浮点（BF16），2 字节一个参数。
14.8B × 2 B ≈ 29.6 GB，装不下。Q4_K_M 是 4 位量化（混合精度，重要层多留几位），
平均 4.5 bit/参数 → 14.8B × 4.5 / 8 ≈ 8.3 GB，实测文件 8.64 GB。

**KV cache**：推理时每个 token 的 Key/Value 要留在显存里供后续 token 注意力查询。
大小 ≈ `2 × 层数 × 头数 × head_dim × 序列长度 × batch × 字节数`。
这就是"上下文越长越吃显存"的原因，也是 vLLM 的 PagedAttention 要解决的问题（把 KV cache 分页管理，减少碎片）。

**这台机器的账本**（实测 `nvidia-smi`）：

| 项 | 占用 |
|---|---|
| qwen3:14b（Q4_K_M） | 8.99 GB |
| 克隆 TTS（0.6B） | 2.5 GB |
| 显示/桌面 | ~1 GB |
| **合计** | 约 12.5 / 16.3 GB |

之前还挂着 faster-whisper（2 GB），14B 一上就只剩 1.3 GB 空闲，最后把 ASR 整个删了 ——
**这就是"显存是硬约束"的真实体感**。

### 4.4 为什么从 9B 换到 14B（有对照数据）

同一个 prompt、同一句话输入：

| | qwen3.5-unc:9b | qwen3:14b |
|---|---|---|
| 回复开头 | "练志，你这一声'橘姐'叫得我心都要化了！刚才那首邓紫棋还没唱顺呢…" | "喵~你这么突然说喜欢我，我都不好意思了啦。不过…你是不是被我可爱到啦？" |
| 和历史回复的相似度 | 0.90（几乎逐字复读） | 不再提旧话题 |
| 冷启动 | 6 s | 22 s（第一次加载，之后常驻） |
| 显存 | 6.5 GB | 9 GB |

结论：**小模型不只是"知识少"，它在长上下文里更容易抄自己**。
这是很典型的"模型容量 → 指令跟随能力"的体现，不是 prompt 能完全补的。

### 4.5 提示词工程：这个项目的 system prompt 长什么样

四段固定顺序（`host/persona.ts`）：

```
① 人设正文（来自配置，6 行）
② 你的名字是"大肥橘猫"。
③ 时间背景（现算，不缓存）
④ 【历史】时间标注说明（只在这一轮有历史时追加）
⑤ 然后是记忆库拼出来的两段（见第 5 节）
```

人设正文里写死的几条，每一条都是踩坑换来的：

| 写法 | 解决什么 |
|---|---|
| "自称小橘或橘姐，绝不自称别的名字" | 模型会自己发明称呼 |
| "对方叫练志，只叫他练志，绝对不要叫他阿泽" | **它把测试数据里的人名当成了用户**，清库后仍然沿用 |
| "回复只写说出口的话：不要写动作、表情、旁白，也不要用括号" | 14B 爱写 `（歪着脑袋，用爪子碰了碰你）`，这段会被 **TTS 一字不差念出来** |
| "有些事是几天前的，别当成刚刚发生" | 它把 2 天前的对话说成"刚才" |
| "别重复你以前说过的句子" | 复读 |

> **面试点**：prompt 里的每一条约束，最好都能说出"不加会怎样"。
> 说不出来的那条，通常可以删。

### 4.6 三个失败模式（都是真踩过的）

**① 思考型模型把 token 全烧在 reasoning 上**

现象：请求 200，但 `content` 是空字符串，应用报"生成失败"。
原因：qwen3 系列默认先输出一段 `reasoning`，`max_tokens` 被它吃光，正文还没开始就 `finish_reason=length`。
修复：请求里带 `reasoning_effort: "none"`。**`think:false` 在 `/v1` 接口上无效**，只有这个参数生效。

> 这类问题的排查套路：先打印 `finish_reason` 和 `usage`，再打印 `message` 的**全部字段**
> （不只是 `content`）。空回复十有八九是 token 花在了别的地方。

**② 超时上限被 schema 卡死**

`timeoutMs` 的 zod 校验是 `1000..60000`，我写了 90000，应用直接起不来，报
`Cannot securely load standalone AI settings.` —— 这个异常**同时覆盖"读盘失败"和"校验失败"**，
只看报错会往文件权限上查半天。

> **面试点**：错误信息的分辨率很重要。一个异常覆盖两类原因，就是可维护性债。

**③ 复读（最像"AI 缺陷"的一个）**

模型不是在回忆，是在**读自己 19 分钟前的原话**。因为上下文里"同一句话 + 当时的回答"成对存在，
对模型来说最省力的续写就是抄一遍。三处一起改：

1. `ageTextOf()`：时间戳从 `[11月7日 15:36]` 变成 `[11月7日 15:36，2天前]`——日期要它自己减，
   相对跨度它直接读；
2. `defuseRelativeTime()`：超过 2 小时的旧回复里，"刚才/刚刚"替换成"那时"，跨日"今天"换"那天"
   （**只改送进模型的副本，不动数据库**）；
3. `repeatScore()` + 重试：生成完和历史上自己每句话比相似度，超阈值就带"换个说法重写"重新生成一次。

## 5. 记忆系统（核心章节，面试最容易被追问）

### 5.1 为什么不能只靠上下文窗口

大模型是**无状态**的：每次请求都要把"它该知道的一切"重新塞进去。
塞不下的部分就真的消失了。三个现实约束：

| 约束 | 具体数字 |
|---|---|
| 上下文有上限 | qwen3 默认 32K token，但塞满会：慢、贵、**中间内容被稀释**（lost in the middle） |
| 一轮对话 3K token 起 | 人设 1.5K + 历史 1K + 召回 0.5K |
| 聊一个月就爆 | 100 轮 × 平均 200 字 ≈ 2 万字，早超了 |

所以标准解法是 **RAG（Retrieval-Augmented Generation）**：
不全塞，只在需要时检索少量相关片段塞进去。

### 5.2 三层结构

```
┌─ 原文层 messages ────────────────────────────────────────────┐
│ 每一句对话原样存。这是"本体"，不可丢。                          │
│ 用途：检索回来后给模型看原话，语气和细节都在                     │
└──────────────────────────────────────────────────────────────┘
┌─ 事实层 memories ────────────────────────────────────────────┐
│ 从原话里抽出的短结论：「她对花生过敏」「她住杭州」               │
│ 用途：比原文更"确定"，召回时优先占位                            │
└──────────────────────────────────────────────────────────────┘
┌─ 情绪权重（不是一张表，是一个函数）──────────────────────────┐
│ affectOf(text) → {valence, arousal, dominance, emotion}      │
│ 用途：调制遗忘速度（越强情绪褪色越慢），不改内容                │
└──────────────────────────────────────────────────────────────┘
```

SQLite 表结构（`host/memory/store.ts:99`）：

```sql
PRAGMA journal_mode = WAL;      -- 读写并发：边写边查不互相锁
PRAGMA synchronous = NORMAL;    -- 性能与安全的折中（掉电可能丢最后几条）

CREATE TABLE messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  pet_id TEXT NOT NULL, role TEXT NOT NULL,
  content TEXT NOT NULL, ts INTEGER NOT NULL, image_name TEXT,
  vec BLOB                       -- 后加的列，ensureColumn 做的迁移
);
CREATE UNIQUE INDEX ux_messages_ts_role ON messages(pet_id, ts, role);
CREATE INDEX ix_messages_pet_ts ON messages(pet_id, ts);

CREATE TABLE memories (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  pet_id TEXT NOT NULL, kind TEXT NOT NULL, content TEXT NOT NULL,
  importance REAL DEFAULT 0.5, confidence REAL DEFAULT 0.8,
  valence REAL, arousal REAL, dominance REAL, emotion TEXT,
  source_ts INTEGER, created_at INTEGER NOT NULL,
  last_used_at INTEGER, access_count INTEGER DEFAULT 0,
  archived INTEGER DEFAULT 0, vec BLOB
);
CREATE INDEX ix_memories_pet ON memories(pet_id, archived, created_at);
```

> **面试点**：为什么"原文"和"事实"分两张表？
> 因为它们的**生命周期和可信度不同**。原文是不可变的流水账；事实会被后续对话修正
> （"她以前讨厌出差"→"现在能接受了"），而且事实的召回优先级更高。
> 放一张表里就得加一堆布尔字段来区分，查询也会变丑。

### 5.3 写入路径（两道）

```
chatWithPet()
  ├─ 同步：写 memory.json（这是唯一真相，人可读、可回退）
  └─ 异步：memoryDb.appendTurn()   ← 不 await，写库失败只记日志，绝不影响回复
        ├─ insertMessage(role, content, ts)   原文进 messages
        └─ absorbFacts(userText)              抽事实进 memories
```

**"唯一真相"选择 JSON 而不是数据库**，是个刻意的取舍：

| | memory.json | memory.db |
|---|---|---|
| 可读性 | 直接打开就能看 | 要工具 |
| 回退 | 删库自动重建 | — |
| 检索 | 不可能 | 快 |

所以采用了**双写 + 单向同步**：`memory.json` 是真相，`memory.db` 是它的可检索镜像。
`syncTurns()` 在每只宠物第一次对话时，把 JSON 里缺的历史补进库（靠唯一索引去重，不用自己判重）。

> **面试点**：这是"数据库是索引，不是真相"的一个落地例子。代价是双写要一致，
> 所以写入必须容错——库挂了只记日志。

### 5.4 关键词抽取：中文没有空格怎么办

英文 `"I like coffee"` 直接按空格切，`like` 就是一个词。
中文 `"我对花生过敏"` 整句是一个字符串，没法切。

标准做法是分词（jieba / HanLP），但引入一个大依赖只为了检索，不划算。
这里的做法是 **n-gram 滑窗**（`store.ts:181`）：

```ts
for (const run of query.match(/[\u4e00-\u9fff]+/g) ?? []) {
  if (run.length <= 4) { push(run); continue; }        // 短句整句留用
  for (let i = 0; i + 2 <= run.length; i++) push(run.slice(i, i + 2));  // 长句切两字
}
// 英文/数字按整词
for (const word of query.toLowerCase().match(/[a-z0-9_]{3,}/g) ?? []) push(word);

out.sort((a, b) => b.length - a.length);   // 长词更具体，优先保留
return out.slice(0, 12);
```

「我对花生过敏」→ `['花生','过敏','对花','生过','敏'(丢弃，<2字)]`。

**为什么两字而不是三字**：中文两字词的覆盖率最高；三字会漏掉"过敏"这种两字词。
代价是"生过"这种噪声片段——靠后面的打分（长词权重高）和停用词表压下去。

> **面试点**：这是"用统计方法替代语言学工具"的典型权衡。
> 也可以用 SQLite 的 FTS5，但**中文在 FTS5 里是坏的**：
> `tokenize='unicode61'` 把整句当一个 token（搜"乳腺癌"命中 0 条）；
> `tokenize='trigram'` 只支持 ≥3 字（"房东""复查"全 0 命中）。
> 最后改用 `LIKE '%词%'` 直扫 —— 580 行的库，几千条记录，毫秒级返回，够用。

### 5.5 向量检索（重点，面试必问）

**embedding 是什么**：把一段文本映射成一个定长向量，语义相近的文本向量夹角小。
`bge-m3` 输出 **1024 维**的 float。

**余弦相似度**：

```
cos(a, b) = (a · b) / (|a| × |b|)
```

范围 [-1, 1]，越接近 1 越像。代码里 `cosine()` 还会处理维度不等 / 零向量（返回 0），
否则会除零或算出 NaN。

**为什么能"换个说法也找得到"**：

| 用户这句话 | 库里那句话 | 关键词重叠 | 余弦 |
|---|---|---|---|
| 肚子疼得厉害 | 胰脏那边不舒服 | 0 | 0.61 ✅ |
| 那个环保的活儿弄得怎么样了 | 海洋塑料污染的汇报材料 | 0 | 0.569 ✅ |
| 吃面的地方是不是换老板了 | 楼下面馆换人了 | 0 | 0.58 ✅ |

阈值 `VEC_MIN_SIM = 0.52`，低于这个值就当没找到（**阈值比模型更重要**：
调低了全是噪声，调高了等于没做）。

**存储**：SQLite 存 `BLOB`，每个 float32 用 `DataView` 显式小端写入：

```ts
const encodeVec = (v: Float32Array): Uint8Array => { /* 4 字节 × 1024 = 4 KB */ }
```

一条 1024 维向量 = 4 KB。一万条 = 40 MB，完全放得下。

**检索方式**：暴力扫（brute force）。

```
1500 条 messages + 500 条 memories，每条算一次 1024 维点积
= 2000 × 1024 ≈ 200 万次乘加 ≈ 1–3 ms
```

所以不需要 ANN（HNSW / IVF / FAISS / pgvector）。**规模决定架构**：
一万条以下暴力扫永远够快，上了百万级才需要近似索引。

> **面试点**：被问"为什么不用向量数据库"，答案是"我的数据量不需要，而且多一个服务就多一个故障点"。
> 能说清"什么时候才需要"（百万级 / 多租户 / 需要增量索引）比背产品名强。

**回填（backfill）**：老数据没有向量怎么办？

```ts
// 单飞（single-flight）：同时只有一次回填在跑，避免并发重复调用 embedding
SELECT id, content FROM messages WHERE vec IS NULL AND length(content)>=4 ORDER BY id DESC LIMIT 32
```

每轮对话后 `void backfillVectors()`（不 await），慢慢补齐。**为什么不阻塞**：
embedding 一次要 15–40 ms，串在回复路径上会被用户感知到。

### 5.6 混合打分（三路合流）

单靠关键词会漏同义改写，单靠向量会漏精确匹配（人名、数字）。所以两路都做，然后合流。

```
① 事实层（关键词命中）
   score = hit * 1.6 + 0.5        // hit = 命中的关键词长度和

② 原文层（关键词命中）
   score = hit * (0.4 + decay) + roleBonus
   decay = 0.5 ^ (ageDays / halfLife)
   roleBonus = 0.3（用户亲口说的）, 0（AI 自己说的）

③ 语义层（余弦）
   score = 3.2 * sim * (0.4 + decay) + bonus
   事实层不衰减（decay = 1）
```

几个设计决策值得记：

| 决策 | 理由 |
|---|---|
| 事实层 `+1.6` / `+0.5` 固定加成 | 事实是"她亲口说过的结论"，同分时应该压过原文 |
| 向量权重 `3.2` 远大于关键词 | 余弦在 [0.52, 1] 之间波动，不放大就跟关键词不是一个量级 |
| 同一句两边都命中取高分 | 否则一条记忆占两个名额，6 个坑位只剩 3 条信息 |
| 事实层不随时间衰减 | "她对花生过敏"不该因为过了半年就不重要 |
| 最终按 `ts` 正序输出 | 拼进 prompt 时读起来像"回忆"，而不是倒放 |

**返回给模型的样子**（`formatRecall`）：

```
【关于她，你确定知道的事】
- 她对花生过敏
- 她住杭州
一律以这里为准：直接照着回答，不要反问，不要改口。

【你想起的旧事】（更早的对话，按时间排序，只在贴题时提一句）
- 2026-11-05 她：我下周要去杭州出差，客户那边不太累
- 2026-11-03 她：楼下面馆换老板了
```

> **面试点**：为什么要在提示词里写"一律以这里为准"？
> 因为模型会把"检索到的资料"当成"可以质疑的信息"，问它"我对什么过敏"它可能反问
> "你过敏吗？"。加上这句后从 50% 变成 100% 直答。

### 5.7 遗忘曲线与情绪权重

原设计抄的是艾宾浩斯遗忘曲线：

```
保持率 = 0.5 ^ (经过天数 / 半衰期)
```

半衰期默认 30 天，但**情绪强的记忆褪色更慢**：

```ts
strength = |valence| × arousal          // 情绪强度：越极端、越激动，越大
halfLife = 30 × (1 + 0.9 × strength)    // 最多放大 1.9 倍（57 天）
decay    = 0.5 ^ (ageDays / halfLife)
```

`affectOf()` 用一张 8 条规则的中文情绪词表（喜悦/疲惫/痛苦/恐惧/愤怒/悲伤/焦虑/释然），
每条带 `valence`（正负）/ `arousal`（激动程度）/ `dominance`（掌控感）。

**为什么不用大模型打情绪标签**：每条消息都调一次模型，成本和延迟都不可接受。
规则层先挡掉 90%，这也呼应了"规则在前、模型在后"的工程原则。

> **面试点**：这个设计对应心理学里的 **情绪一致性记忆**（mood-congruent memory）
> 和 **闪光灯记忆**（flashbulb memory，高唤醒事件记得特别牢）。
> 但要注意 **fading affect bias**：日常负面情绪消退得比正面**快**，
> 所以"负面一律延长"是错的——只有高强度 + 自我相关的才延长。

### 5.8 事实抽取的三个坑

用正则从原话里抽事实（`extractFacts`，6 条模式），踩了三个坑：

| 坑 | 现象 | 修复 |
|---|---|---|
| 问句被当事实 | "我对什么过敏？"抽出"我对什么过敏"，和自己的提问撞车，模型答"被问懵啦" | `looksInterrogative()`：含"什么/啥/哪/谁/多少/怎么"整条丢弃 |
| 第一人称残留 | "我对花生过敏"原样进 system，猫以为过敏的是**它** | `m[0].replace(/^我/, '她')`，历史数据用 SQL 迁移 |
| 排序错 | 最贴题的事实被时间序排到中间，模型抓不到 | 事实按分数在前，原文按时间在后 |

### 5.9 和"微调"的区别（必问题）

| | RAG（这个项目） | 微调（Fine-tuning） |
|---|---|---|
| 改的是什么 | 提示词里塞什么 | 模型权重 |
| 新知识 | 立刻生效，改数据库即可 | 要重新训练 |
| 成本 | 一次检索几十 ms | 一张卡几小时到几天 |
| 可解释 | 能指出"它是因为这条记忆才这么答" | 说不清 |
| 适合 | **事实性、个性化、会变的信息** | 风格、格式、固定任务 |

标准答案：**"记住你是谁"用 RAG，"说话像谁"才考虑微调。**

## 6. 语音合成（TTS）

### 6.1 三段式结构

```
文本 → ① 文本前端 → ② 声学模型 → ③ 声码器 → 波形
       (分词/数字读法/    (文字 → mel 频谱     (mel → 采样点
        韵律预测)          或离散 token)        24 kHz PCM)
```

这个项目用的 Qwen3-TTS 属于**第二代架构**：不走 mel 频谱，而是把音频压成**离散 token**
（12 Hz 的 tokenizer，一秒 12 个 token），然后用一个**语言模型**去"续写"这些 token。
好处是可以复用一个 LLM 的解码框架，坏处是——**它也是自回归的，速度慢**。

### 6.2 零样本克隆是怎么回事

不需要训练，只要给一段参考音频（3–15 秒）+ 它的**逐字稿**，模型就能模仿音色。

原理上分两条路，实际是混合的：

1. **说话人向量（speaker embedding / x-vector）**：一个编码器把参考音频压成一个定长向量，
   代表"音色"这个抽象属性（音高、共振峰分布、语速习惯）；
2. **上下文学习（in-context learning）**：把参考音频的 token 序列直接拼在待合成文本前面，
   让模型"接着往下说"——本质是 few-shot prompting，只不过 prompt 是音频。

**`ref_text` 为什么必填**：模型需要知道"这段音频对应哪些字"，才能建立音色和发音的对应关系。
不给逐字稿，它会把参考音频当成"要念的内容"接着念下去。

> 这就是为什么第一次给的是 35 秒的 `11月7日.mp3` 我问你要不要文字稿——
> 模型不会自己转录。

### 6.3 这个项目里的实测

| 指标 | 数值 |
|---|---|
| 模型 | Qwen3-TTS-12Hz-0.6B-Base（Apache 2.0） |
| 体积 | 2.34 GB / 12 个文件 |
| 加载 | 模型 2.4 s + 参考音色 prompt 15.1 s（一次性） |
| 显存 | 2.02 GiB，峰值 2.59 GiB |
| 输出 | 24 kHz 单声道 |
| **RTF** | **1.7–1.95** |

**RTF（Real-Time Factor）= 合成耗时 / 音频时长**。RTF 1.8 意味着合成 10 秒的话要 18 秒。
**这是整个方案最硬的瓶颈，也是"说到一半就没了"的真正原因。**

### 6.4 分句流水线与"感知上的流式"

既然合成比播放慢，能做到的是**别让它等**：

```
回复 105 字 → speechPieces() 切成 4 片（17 / 39 / 26 / 23 字）
  ├─ 立刻请求第 1 片 ────────────► 6–9 s 后开始播
  ├─ 播第 1 片的同时请求第 2 片 ──► 播完时第 2 片已就绪
  └─ ...                          实测片间停顿 8.9 / 4.2 / 2.9 s
```

关键代码（`shared/voice.ts`）：

```ts
let pending = requestSpeech(pieces[0]);
for (let i = 0; i < pieces.length; i++) {
  const blob = await pending;
  if (i + 1 < pieces.length) pending = requestSpeech(pieces[i + 1]);  // 先发请求
  await playSpeech(blob, i === 0 ? onHeard : undefined);               // 再播这一片
}
```

**两个细节**：

- `playSpeech` 必须等 `audio.onended` 才 resolve，否则多片会叠在一起播；
- 切分规则：先按句号/问号/叹号切，超长的再按逗号切，太短（<8 字）的并回上一片，
  总量上限 120 字（`VOICE_SPEECH_TOTAL_MAX`）。**切太碎会让语气断掉，切太粗又回到长等待。**

> **面试点**：这是"用工程手段掩盖模型性能不足"的典型——模型不会流式，就在应用层做假流式。
> 真正解法是流式 TTS（边生成边出包），但那要模型侧支持。

### 6.5 工程细节（都很小，但每个都能问）

| 细节 | 为什么 |
|---|---|
| 返回 **mp3** 而不是 wav | 插件缓存路径写死 `.mp3`（`voice/cache.ts:19`），淘汰逻辑只扫 `.mp3` |
| 用 `lameenc` 编码 | 没装 ffmpeg；`lameenc` 是纯 Python 绑定，4.9 s 音频编码 26 ms |
| 参考音频要预处理 | 裁静音（-40 dB 门限）+ 重采样到 24 k + 峰值归一到 -1 dBFS。**原始 mp3 直接给，合成出来几乎全静音**（rms -49.9 dB） |
| 超时 120 s（provider）/ 180 s（客户端） | 克隆音色 37 字要 17.4 s，60 字必然超 30 s 老口径 |
| TTS 起子进程而非进程内跑 | Python 生态（torch / transformers）和 Node 完全不同栈，只能跨进程 |
| 子进程要预热 | 模型加载 2.4 s + 音色 15 s，不预热第一条要等 17 s |

### 6.6 "声音不像"该怎么诊断

用户反馈"都不是很像，语气没起伏"。这是**评估问题**，不是调参问题。可拆成三件事：

1. **音色像不像**（音高、共振峰）→ 换参考音频；
2. **语气像不像**（韵律、停顿）→ 参考音频里的情绪必须和目标一致，
   给一段"烦死了"的短句当参考，就别指望它念出温柔的长句；
3. **模型本身的上限** → 0.6B 的表达力有限，1.7B 会明显好，但要 5–6 GB 显存。

**参考音频质量的量化检查**（写了个 `audio_check.py`）：

| 文件 | 时长 | 有声占比 | 发声段数 | 结论 |
|---|---|---|---|---|
| 打打麻将.mp3 | 7.55 s | 77.5% | **12 段** | 疑似混了背景音 |
| 我回来了.mp3 | 8.57 s | **42.3%** | — | 静音太多，克隆失败 |
| 你快去吃饭吧.mp3 | 2.40 s | — | peak -12.7 dB | 偏轻 |
| 烦死你了.mp3 | 2.77 s | — | peak **-1.7 dB** | 最干净，最终选它 |

> **面试点**：这是"数据质量 > 模型能力"的实例。同一套参数，换参考音频结果天差地别。

## 7. 语音识别（已移除，但值得会）

> 2026-11-09 按需求删除了。技术和数据留着，面试可以讲，因为链路是完整的。

**Whisper 的结构**：Encoder-Decoder Transformer。
音频先转成 **log-mel 频谱图**（80 通道），过 encoder；decoder 自回归出文字 token。
它不做强制对齐，所以是"端到端"的语音识别。

**CTranslate2** 是它的推理加速引擎：把 PyTorch 的权重转成自己的格式，
用 int8 / float16 量化 + 算子融合，CPU 上也能跑得动。

实测（large-v3-turbo，1.51 GB）：

| 场景 | 耗时 | RTF |
|---|---|---|
| 冷启动第一次 | 19.5 s | 4.43（含 cuBLAS 初始化） |
| 热态 1.55 s 音频 | 101 ms | 0.07 |
| 热态 2.34 s 音频 | 123 ms | 0.05 |

**两个坑**：

- **cuBLAS 找不到**：ctranslate2 只认系统 PATH 里的 `cublas64_12.dll`，而 CUDA 装在 torch wheel 里。
  修法是在 `import ctranslate2` **之前** `os.add_dll_directory(torch/lib)` 并把目录塞进 PATH；
- **冷启动 20 秒**：必须在应用启动时用一段 0.6 s 静音预热一次，否则用户第一句话要等 20 秒。

## 8. 桌面交互层（Electron）

### 8.1 三进程模型

| 进程 | 干什么 | 能不能碰 Node API |
|---|---|---|
| **主进程** | 创建窗口、托盘、全局状态、HTTP 服务 | ✅ 全权限 |
| **渲染进程** | 画面（宠物、气泡、对话窗） | ❌ 默认沙箱 |
| **preload** | 桥梁：把白名单 API 挂到 `window.petBridge` | ✅ 但只能按需暴露 |

这就是 **contextIsolation**：渲染进程拿不到 `require`，能碰什么全靠 preload 显式给。
好处是"页面被注入恶意脚本也拿不到系统权限"。

### 8.2 透明窗的几个关键配置

| 配置 | 作用 | 不设会怎样 |
|---|---|---|
| `transparent: true` | 背景透明 | 一个白方块糊在桌面上 |
| `frame: false` | 去掉标题栏 | 有个 Windows 蓝条 |
| `alwaysOnTop: true` | 置顶 | 被别的窗口盖住 |
| `skipTaskbar: true` | 不出现在任务栏 | 点一下宠物任务栏多一个窗口 |
| `setIgnoreMouseEvents(true, { forward: true })` | **点击穿透**：透明处点击落到下面的窗口 | 整个屏幕都是这个窗口，别的地方点不动 |
| `showInactive()` | 显示但不抢焦点 | 一启动就把你的输入焦点抢走 |

**点击穿透是这类应用的灵魂**：窗口是全屏那么大的（因为宠物可以拖到任何位置），
但只有宠物身体那一小块要接收鼠标。做法是**逐帧算 alpha**，命中的地方开鼠标事件、其余穿透。

> 这里有个副作用值得说：**窗口不聚焦就收不到键盘事件**。
> 所以"悬停在宠物上按 M 说话"这种功能，必须先调 `requestKeyboardFocus()`；
> 而 `showInactive()` 出来窗天然没有焦点，于是一开始按键全无反应。

### 8.3 单实例锁

```ts
const locked = app.requestSingleInstanceLock();
if (!locked) { app.exit(0); } else { await boot(); }
```

**为什么必须有**：HTTP 端口、SQLite 文件、TTS 子进程都是独占资源。
开两个实例会出现"两个宠物同时说话"。

**一个反直觉的坑**：`--user-data-dir=<另一个目录>` **绕不过单实例锁**。
因为锁是 Electron 按应用身份（`app-user-model-id`）建的，不是按用户目录。
排查"程序一启动就悄悄退出、连日志都不写"时，先怀疑这里。

### 8.4 鉴权（本地服务也要）

HTTP 只监听 `127.0.0.1`，但**同机其它程序也能访问**。所以：

- GET/HEAD 基本放行（`/state`、`/config`、`/assets`）；
- **POST 一律要令牌**：请求头 `X-DSH-Pet-Token` 或 cookie `dsh_pet_token`；
- 令牌每次启动随机生成，只存在主进程内存里；
- 渲染端的 cookie 由 `installDesktopAuth()` 注入，所以页面里 `fetch(..., {credentials:'include'})` 能过。

> 这是"本地 ≠ 可信"的例子。127.0.0.1 只挡住了外网，挡不住本机的恶意软件。

## 9. 构建与工程化（坑最多的部分）

### 9.1 TypeScript + rolldown/tsdown

源码是 TS（ESM，`.ts` 后缀直接 import），产物是 4 个 bundle：

| 产物 | 是什么 |
|---|---|
| `lib/app.js` | 独立桌面应用入口（Electron 主进程） |
| `lib/index.js` | 作为 DSH 插件时的入口 |
| `lib/standalone.js` | CLI 模式 |
| `lib/client.js` | 浏览器端（DSH Web 里的宠物） |
| `runtime/electron-helper/shared-core.js` | 窗口栈共享逻辑，`window.PetShared` |

用 **rolldown**（Rust 写的打包器，Vite 团队在做，目标是替代 Rollup）通过 **tsdown** 驱动。

### 9.2 三个 Windows 特有的坑（都很有讲头）

**① pnpm 的 junction 和 `fs.realpathSync`**

pnpm 默认用**符号链接 + 硬链接**组织 `node_modules`。
Windows 上没有真正的 symlink 权限时，会退化成 **junction**（目录联接）。

问题：Node 24 的 `fs.realpathSync` **不解析 junction**（原样返回 junction 路径）→
通过 junction 加载的包找不到自己的传递依赖，报 `Cannot find module 'debug'`。

修法有两个：
- 从包的**真实路径**启动（`.pnpm/tsdown@0.8.0/.../bin/tsdown.js`）；
- 或者干脆 `pnpm install --node-linker=hoisted`（退化成 npm 式的扁平 node_modules）。

**② rolldown 的 Windows 路径 bug**

```
Could not load C:Users\lianzhi\...\node_modules\zod\index.js (os error 3)
```

注意 `C:Users` —— **盘符后的反斜杠被吃掉了**。结果是所有被内联的依赖全部加载失败。
绕法：把这些依赖**外部化**（`external: ['zod','openai',...]`），运行时从 node_modules 解析。

**③ PowerShell 的编码**

`Get-Content -Raw | Set-Content` 会把 UTF-8 中文**变成 GBK 乱码**（Windows PowerShell 5.1）。
所以改文件一律用专门的编辑器/工具，不用管道回写。

### 9.3 启动器为什么要用 VBS

```
启动桌宠.vbs  →  wscript.exe  →  Run("node.exe start-app.mjs", 0, False)
```

为什么不用 `.cmd`：**cmd 会闪一个黑框**。VBS 的 `Run(..., 0, False)` 是隐藏窗口 + 异步。

**VBS 必须存成 UTF-16LE + BOM**：wscript 按 ANSI 读文件，中文路径会直接读坏。

## 10. 性能账本（面试最爱问"怎么优化的"）

### 10.1 延迟分解

| 环节 | 现状 | 优化空间 |
|---|---|---|
| LLM 出完整回复 | 0.6–1.5 s | 流式输出可以更早开始 |
| 检索（含 embedding） | 15–40 ms | 已经很小 |
| 首片 TTS | 6–9 s | **最大瓶颈**，RTF 1.8 |
| 片间停顿 | 2–9 s | 切片更细 / 换流式 TTS |
| 播放 | 实时 | — |

### 10.2 已经做过的优化

| 手段 | 效果 |
|---|---|
| 记忆写库改异步（`void appendTurn`） | 回复不等落盘 |
| 向量回填后台单飞 | 不阻塞对话 |
| 分片并行（下一片合成与这一片播放重叠） | 片间停顿从 20 s 级降到 2–9 s |
| embedding 结果缓存（`keep_alive: 30m`） | 避免模型被换出后重加载 |
| TTS 子进程常驻 + 启动预热 | 首条不等 17 s |
| 提示词长度控制（≤6 条记忆、单条 80 字） | 输入 token 减半 |

### 10.3 没做但知道怎么做

| 想法 | 代价 |
|---|---|
| 流式 TTS（边生成边出音频包） | 要模型侧支持，Qwen3-TTS 有 streaming API |
| 换 0.6B → 1.7B | 显存 +3 GB，但这台机器已经满了 |
| 首片切更碎（8–10 字） | 首声压到 4 s，但语气会更断 |
| 上 ANN 索引（HNSW） | 现在数据量根本不需要 |

## 12. 面试问答 25 题

**Q1. 一句话说清这个项目**
> Electron 桌面宠物 + 本地大模型 + 三层记忆库 + 克隆语音。核心在记忆检索，模型只是个生成器。

**Q2. 为什么不用现成的聊天框架？**
> 现成框架解决的是"多轮对话 + 工具调用"，不解决"记住三个月前的一句话"。
> 记忆检索是独立能力，跟 UI 框架无关。

**Q3. 上下文窗口那么大，为什么还要 RAG？**
> 三个原因：成本（每轮都塞满很贵）、延迟（输入越长首 token 越慢）、**稀释**（中间内容会被忽略）。
> 而且真实需求是"只回忆相关的 3 条"，不是"全文背诵"。

**Q4. 你的检索怎么做的？**
> 三路合流：中文两字滑窗的关键词 `LIKE` 匹配、`bge-m3` 的 1024 维向量余弦、以及事实层加成。
> 打分 = 命中长度 × 时间衰减 + 角色加成；向量路单独加权 3.2。最后取 top 6 拼进 prompt。

**Q5. 为什么不直接上向量数据库？**
> 2000 条记录暴力扫 1–3 ms，多一个服务就多一个故障点。
> 上百万条或要增量索引时才值得。

**Q6. 余弦相似度阈值怎么定的？**
> 0.52。定高了（0.7）同义改写召回不到；定低了（0.4）全是噪声。
> 用 10 组"换说法"的测试用例调的，现在能做到"换个说法也能捞回来"。

**Q7. embedding 是什么原理？**
> 一个双塔模型，把文本映射到定长向量空间，训练目标是让语义相近的文本向量接近（对比学习）。
> 它不是"理解"，但足够做"相似"这个近似。

**Q8. 新数据没有向量怎么办？**
> 后台回填：每轮之后挑 32 条 `vec IS NULL` 的批量算，单飞（同时只有一次在跑）。
> 不 await，避免阻塞回复。

**Q9. 记忆忘了怎么办？**
> 半衰期衰减：默认 30 天，情绪强度高的最多延长到 57 天。
> 事实层不衰减（"她对花生过敏"不该随时间消失）。

**Q10. 怎么防止它胡说八道？**
> 三道：检索到的内容用"一律以这里为准"固定住；事实层抽取用正则不用模型（可控）；
> 回复后做复读检测，撞了就重生成。

**Q11. 什么是复读问题？你怎么发现的？**
> 模型会照抄自己之前的回复（相似度 0.9）。根因是上下文里"同一句话 + 当时的回答"成对存在。
> 解法三条：加相对时间前缀、把旧回复里的"刚才"改成"那时"、生成后自检相似度并重试。

**Q12. 你的 prompt 怎么组织的？**
> 四段固定顺序：人设正文 → 名字声明 → 时间背景（现算）→ 历史时间说明；再接记忆库的两段。
> 有一条硬约束：**拼装点唯一**，不给名字和时间开占位符配置，否则会出现第二个拼装点。

**Q13. 为什么用 OpenAI 兼容协议？**
> 换模型只改 `baseURL` + `model` 两个字符串。Ollama / vLLM / DeepSeek / 通义都说这个协议。

**Q14. temperature / top_p / top_k 区别？**
> temperature 缩放 logits（改了整条分布的形状）；top_p 是核采样（截断累计概率尾部）；
> top_k 是硬截断（只留前 k 个）。三者作用点不同，通常只调其中一两个。

**Q15. 量化是怎么省显存的？**
> Q4_K_M 平均 4.5 bit/参数，14.8B × 4.5/8 ≈ 8.3 GB。代价是精度损失，
> 表现为长尾知识变差、数学变弱，日常对话几乎无感。

**Q16. KV cache 是什么？**
> 自回归生成时，每个 token 的 K/V 要留着供后面的 token 做注意力。
> 它让生成是 O(n) 而不是 O(n²)，但占显存随上下文线性增长。PagedAttention 就是管它的。

**Q17. TTS 怎么做到克隆音色？**
> 零样本克隆：参考音频编码成说话人向量 + 音频 token 序列拼在文本前做 in-context learning。
> `ref_text` 必填，模型不会自己转录。

**Q18. RTF 1.8 怎么办？**
> 应用层做假流式：按句切片，第 N 片在播时预取第 N+1 片。
> 停顿从 20 s 级降到 2–9 s。真解法是流式 TTS。

**Q19. Electron 的进程模型？**
> 主进程（Node 全权限，管窗口）、渲染进程（沙箱，管画面）、preload（白名单桥）。
> contextIsolation 保证渲染进程拿不到 `require`。

**Q20. 点击穿透怎么做的？**
> `setIgnoreMouseEvents(true, {forward:true})` + 每帧按 alpha 判断，命中宠物的像素才开鼠标事件。

**Q21. 单实例锁有什么用？**
> 端口、SQLite、子进程都是独占资源。`requestSingleInstanceLock()` 失败直接 `app.exit(0)`。
> 注意 `--user-data-dir` 绕不过它。

**Q22. 你踩过最深的坑？**
> 三个候选：pnpm junction 导致 `fs.realpathSync` 找不到传递依赖；rolldown 吃掉盘符后的反斜杠；
> 思考型模型把 token 烧在 reasoning 上导致空回复（`reasoning_effort:'none'` 才修好）。

**Q23. 如果要做多用户/云端，你改哪里？**
> 记忆库加 `user_id` 分区（现在已经有 `pet_id`）；HTTP 换成带鉴权的网关；
> embedding 和 LLM 换远程服务；SQLite 换 Postgres + pgvector。

**Q24. 这个项目你觉得做得最好的是哪部分？**
> 记忆的三路召回和它的可解释性——能打印出"它是因为这三条记忆才这么答"。
> 以及"数据库是索引、JSON 是真相"这个设计，删库能重建。

**Q25. 哪里做得不好？**
> TTS 是硬伤：RTF 1.8 导致长回复必然有停顿，这是模型能力问题，应用层只能缓解。
> 另外记忆库的"事实抽取"是正则，覆盖不了复杂句式，应该上小模型做抽取 + 人工确认队列。

## 14. 延伸学习（按主题，够用来应付追问）

| 主题 | 要知道什么 | 关键词 |
|---|---|---|
| Transformer | 自注意力、位置编码、为什么能并行 | attention, positional encoding |
| 推理 | KV cache、PagedAttention、batching、投机解码 | vLLM, speculative decoding |
| 量化 | INT8 / GPTQ / AWQ / GGUF 的区别 | quantization, calibration |
| RAG | 切片策略、混合检索、重排（rerank）、评估 | chunking, hybrid search, reranker, recall@k |
| 向量索引 | 暴力 / IVF / HNSW / PQ 的取舍 | ANN, HNSW, product quantization |
| 微调 | LoRA / QLoRA / SFT / DPO 各自解决什么 | LoRA, RLHF, DPO |
| 语音合成 | 声学模型 / 声码器 / 离散 token / 流式 | VITS, HiFi-GAN, RVQ, streaming TTS |
| 语音识别 | mel 频谱、CTC、注意力解码 | Whisper, wav2vec, CTC |
| 桌面端 | Chromium 多进程、沙箱、IPC | contextIsolation, preload |

**几个能撑场面的概念对比**：

- **RAG vs 微调**：RAG 换知识，微调换风格。
- **暴力检索 vs ANN**：万级以下暴力够用；ANN 用召回率换速度。
- **流式 vs 非流式**：流式优化的是"首字延迟"，不改变总耗时。
- **同步 vs 异步写**：影响的是"用户等不等"，不是"数据丢不丢"。
